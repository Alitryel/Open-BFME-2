# Core allocator 32B00: inlined chunk-initializer hypothesis refuted; copy wall unchanged

Blocked verdict, 2026-10-20, model claude-opus-5-5, about 30 minutes. Native range 0x00032B00..0x00032C57 (343 bytes, RET 4). The bank `reverse/attempts/0x00032b00.cpp` is unchanged and still the best body: 341/343, prefix exact through 0x00032C11, align_diff 3 structural regions and 3 register operands. All earlier verdicts and `corealloc-32b00-20261019.md` were read first; nothing below repeats a spelling they rule out except where noted as a control.

## Remaining mismatch (unchanged)

Retail builds the chunk header as `mov edx,eax; or edx,ebx; mov eax,edx` (the raw size in EAX is copied before the OR, the OR result in EDX is copied to EAX for the fencepost offset). Every candidate ORs in place (`or eax,ebx; mov edx,eax`), two bytes shorter. The epilogue also differs: retail `pop edi; mov edx,8; pop esi; store; store; pop ebp; store; store`, ours `pop edi; pop esi; mov edx,8; pop ebp; store x4`.

## Hypothesis tested this run

Retail inlines the three-argument chunk initializer whose out-of-line copy is 0x00031160 (matched in `Code/GameEngine/Source/Common/GapBodiesGE23.cpp`: stores size|flags, zeroes the prior size, writes the 8/8/9 double fencepost, returns the chunk). Its size argument would be a by-value parameter that cl copies before the OR. Evidence for it: 0x31160 performs exactly these operations in this order, and the copy-OR-copy shape feeding a fencepost mask occurs in retail only at the two chunk-init sites 0x32C11 (this body) and 0x333A0 (0x332D0); among all 59,750 matched bodies it appears only at 0x332D0, which reproduces it with an equal-arm hack. Refutation criterion: a visible inline copy of the initializer, inlined here, still ORs in place.

Result: refuted. Static inline, auto-inlined extern, void and chunk-returning forms, a parameter modified in place (`size |= flags`), a const-reference size parameter, and the 0x31160 source spelling all copy-propagate the parameter and OR in place, both in the bank context (8 variants) and in the 0x332D0 home context (4 variants, 0x332D0 then loses its copy too).

## Other findings

- In the home unit `Code/GameEngine/Source/Common/System/Rva00031010Insert.cpp`, replacing 0x332D0's `(1 ? initSize : initSize) | 1` with a local `const unsigned int &initSize = ...;` and `initSize | 1` keeps 0x332D0, 0x334A0 and 0x31010 byte-exact (checked with `build.compile_function`). That is an optional hack reduction for that unit. The same binding (already in the bank) is inert in 0x32B00, even with 0x332D0's exact tail transplanted (pointer copy, named `initFlags`, its fencepost helper).
- Diagnostic only: declaring `chunkFlags` as `unsigned short` (344 B) or `unsigned char` (338 B) makes cl compute the OR in the zero-extended flag temp in EDX and then emit retail's `mov eax,edx`. So retail's raw-size operand was treated as not overwritable at the OR, as a const-reference temp is in 0x332D0 (held in ESI there, in EAX here). In that variant the epilogue pops kept our order although the chain had retail's length, so the epilogue gap may be independent of the copy (n=1).
- A port into the home unit (the unit this row holds out of linking) reaches exact parity with the bank: 341/343, same align_diff, with 0x31010, 0x332D0 and 0x334A0 still byte-exact in the same object. Trial text and the two class-view field splits it needs: `reverse/attempt_support/corealloc-32b00-20261020-home.cpp.txt`.

## Ruled out this run (all 341/343, none produce the copy)

- Grid of 72: size as const reference, plain local or inline expression; with or without a chunk pointer copy; memory_pool `AddDoubleFencepost`, the 0x332D0 static helper or the 0x334A0 volatile-store helper; zero store before or after the size store; both OR operand orders. The const reference is what keeps the prefix (zero in EDX, old next in EDI); without it the zero moves to EDI.
- All 48 declaration orders of `coreSize`, `chunkFlags`, `reservedSize`, `core`, each with the flag assignment first or second.
- Scope-limited const reference, `|=` on a copy, read-modify-write of `chunk[1]`, const-reference header value, pointer-arithmetic and `int`, `long`, `unsigned long` size types, const references bound to converted or named temps, an inline size-returning helper with and without binding, early-return structure, `(flags & 2) != 0` for +0x0C, enum-typed flags, `unsigned char`, `int`, `char` for `notFirst`, `(flags & 3)` in the OR.
- Removing the three volatile descriptor writes only re-hoists the +0x0E store; the tail is unchanged.
- `tools/permute.py 0x00032B00`: 1,165 trials on the current bank, no gain (start and best 0.9785).
