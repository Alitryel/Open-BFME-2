Every instruction outside the first inverse transform (retail +0xB9 to +0x166) matches retail apart from relocation slots. Symbol `?getPosition@LightningEmissionModule@FXParticleSystem@@UAE?AUCoord3D@@MMHH@Z`, RVA 0x0055DDD1, 1295 bytes, flags `/O1 /G7 /arch:SSE /EHsc` as in the r2 bank.

**Remaining mismatch:** only the first `Matrix3D::Inverse_Transform_Vector` call, whose input is the system matrix's own translation. Retail keeps dy, dz and dx in xmm2, xmm0 and xmm1 and sums the Z row as `(A22*dz + A12*dy) + A02*dx`. Our body keeps them in xmm1, xmm2 and xmm0 and sums Z as `(A02*dx + A22*dz) + A12*dy`, which is exactly how retail compiles the second transform (input: the system position at +0x188). So retail's two inlined transforms differ from each other in that one place, while ours are identical.

## Levers that closed the other regions

Each was measured with a fresh object through `tools/align_diff.py`.

1. **Visible select-any copies of `Coord3D::length` (0x00003571) and `Coord3D::normalize` (0x000035B6).** Both compile to retail's bytes in this unit (0 regions each, relocations only). With both bodies visible, cl knows `normalize` does not leak the direction, so `dir` shares `end`'s frame slot and the frame drops from 0x7C to retail's 0x70. Making only `normalize` visible changes nothing, because `length()` still leaks `this`. In the home unit `Code/Libraries/Source/WWVegas/WWMath/coord3d.cpp` both are already `inline` (select-any), so a landed copy does not collide in the link.
2. **`perp` built by the `Coord3D(float, float, float)` constructor.** All reads of `dir` then happen before `perp` is born, so `perp.y` and `perp.z` spill into `dir`'s slot (-0x78, -0x74) and `perp.x` stays in xmm6 for the whole loop, as in retail. Field-by-field stores give `perp` its own slot.
3. **The header `Matrix3D::Inverse_Transform_Vector` together with an inline null-object accessor** `system()` (`m_ptr == 0 ? Make001FCBD7() : m_ptr`, the same idiom as `Rva00563F34FXGate.cpp`) in place of three named `ParticleSystem *` locals. Neither helps alone; together they give retail's operand order and register use for the whole second transform.
4. **`Coord3D *pt = &s_points[i]` in the loop** gives retail's induction pointer `s_points+8` instead of `s_points+4`.
5. `Coord3D dir = delta;` compiles identically to field copies and is kept as the natural spelling.

## Ruled out for the first transform (each compiled identically or measured worse)

- Input spellings: `Vector3(m[0][3], m[1][3], m[2][3])`; a named `Vector3 origin = m.Get_Translation()`; `m.Get_Translation(&pos)` into a named or the output vector; in-place `Inverse_Transform_Vector(m, a, &a)`; output into a `Coord3D` temporary; one shared output temporary for both transforms; a nested scope around the first transform.
- Matrix access: `const Matrix3D *m` instead of a reference; a named `ParticleSystem *sys` for the isLocal test (worse: 5 regions).
- Transform body: a hand-written forceinline helper with scalar or `Vector3` diff, with or without ZH's alias-check pointer, with reversed row order, or with the differences written inline (9 to 15 regions); mixing helper and header between the two calls (9 and 15 regions); `Vector3 up` instead of `Coord3D up`.
- Declaration order of `start` and `end`; `/Ob2`; the `vc71-sp1` compiler profile.

## Next step for a successor

Find what makes retail treat the first transform's inputs differently from the second's. The remaining difference is register colouring and the Z-row association, which follow the operand ranks of dx, dy and dz. In the first transform each difference is `t - t` of a single matrix load. A source that yields the same loads through a different expression (for example a different accessor of the system position or transform, or a BFME 2 helper that wraps the transform) is the next thing to test.
