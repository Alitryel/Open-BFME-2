# 0x000EB6BB: postMul parentheses searched against retail (closer bank)

Result: partial, banked as `reverse/attempts/0x000eb6bb.cpp` under the unchanged symbol `?rva000EB6BB@Rva000EC9C6@@QAEXXZ` (retail 0x000EB6BB..0x000EBFD1, 2326 bytes). Not byte-exact. Model: claude-opus-5-5.

## What changed and why

1. **The non-retail X0 parentheses are gone.** The previous bank wrote row 0's X sum as `(t0 + t1) + t2`, an association retail never computes (retail X0 is `(t2 + t1) + t0`). Every sum is now left to cl's reassociation except row 1's W sum, which is spelled `(t0 + t2) + t1`, exactly retail's association for that sum. Here `tk = a[r][k] * b[k][c]`, with `a` the local transform and `b` the record's transform.
2. **Two WorldBuilder-faithful spellings at no byte cost.** The mesh check re-tests `type<0` as WB 0x89B7E9 does, and the record stores are written firstVertex (+0x624) then buffer (+0x628) as in WB 0x89C12B and Zero Hour. Both compile byte-identically to the same source without them.

Semantics: unchanged apart from float association. The one remaining explicit association is retail's own, so that sum now rounds as retail does; the other eleven sums follow cl's canonical order, as they would from an unparenthesised source.

## How the search was run

A driver generated the bank with each of the twelve postMul sums in one of three spellings (no parentheses, the old bank's `(t0+t1)+t2`, or retail's association), compiled each through align_diff and scored it. Retail's associations, read off the retail SSE code by symbolic execution of the world branch through Translate: X0 (t2+t1)+t0, Y0 (t0+t2)+t1, Z0 (t2+t1)+t0, W0 (t0+t2)+t1; row 1 all (t0+t2)+t1; X2 (t2+t1)+t0, Y2 (t2+t1)+t0, Z2 (t0+t2)+t1, W2 (t2+t1)+t0. 379 configurations were measured (greedy passes over single flips, then every pair and triple of flips from the best retail-only configuration). None dominates the chosen one in all three of regions, memory and register; it is the only configuration with 14 or fewer regions and fewer than 55 memory lines. Configurations that keep the old X0 parentheses reach a higher LCS (`(t0+t1)+t2` on X0 plus retail W1 and X2: 17 regions, m53, r34, LCS 420) but were not banked because that X0 spelling is not retail's arithmetic.

## Ruled out this run

- WorldBuilder's debug body inlines `submul` (its x87 order Z, Y, X, add, add is what an inlined by-value `submul` produces at /Od /Ob1, reproduced with cl 7.1), so BFME 2's header postMul is the original source. The header postMul is still worse than the bank (2308 B, 22 regions, m105, r49), alone and with WB's `vb`/`ib` copies (2319 B, 19, m89, r52).
- At /O1 /G7 /arch:SSE, cl honours explicit parentheses as a reassociation barrier and canonicalises unparenthesised chains; `submul` and the plain expression compile identically.
- Member access (`a[0].X` instead of `a[0][0]`) in the local postMul: 2326 B but 19 to 21 regions and more register lines, on both bases.
- Per-row or block-scoped temporaries in the postMul: 2358 B, 28 regions, m156.
- Statement order of the four temporaries: Y, Z, W, X (retail's computation order) in rows 0 and 1 compiles byte-identically. Adding it to row 2 is worse (2318 B, 23 regions, m133), and W, X, Y, Z in all rows is worse too (2329 B, 26 regions, m110).
- WB's `vb`/`ib` copies, a local Translate in retail's association, WB's named reference to the record transform and one shared `curTree` for both loops: all worse on the new base too.

## Remaining mismatch

At the merge retail keeps m20 in xmm7 and ours keeps m22, and m01/m02 sit in swapped registers (xmm6/xmm5 against retail's xmm5/xmm6). From there the Scale, postMul and Translate schedules differ in one large region pair (retail +0x2CA..+0x387). Eleven of the twelve sums still use cl's canonical association rather than retail's; forcing all twelve gives retail's merge register set but a shorter, worse-aligned body (2297 B), so the association and the allocation are coupled and need to be solved together.
