## What moved the body

The body now follows WorldBuilder's structure throughout (WB 0xA0E990 and its callees, read with `tools/wb_show.py`):

1. The blend is a member of the first matrix with the loop inside, in WB 0xA0ECA0's operand order, reading rows through members (`v[r].X`, `tm1.v[r].X`), as WB does.
2. The single-bone path calls `TransformPositionArray` on the pivot transform (WB 0xA0EE10, `bonetransform.h`), with WB's exact expressions: `x=W*v.X+(Y*v.Z-v.Y*Z)`, `y=W*v.Y-(X*v.Z-v.X*Z)`, `z=W*v.Z+(X*v.Y-v.X*Y)`, `w=-(X*v.X+Y*v.Y+Z*v.Z)`, `out.X=x*W-w*X+(z*Y-y*Z)+T.X` and so on.
3. The matrix rows are a Vector4-like type, and the scale loop is WB's `tm0[j]*=w0; tm1[j]*=w1;`.
4. One `int i` serves both stream loops (WB local_4).
5. Each output row of both helpers is wrapped in outer parentheses, as the WWMath header writes `Transform_Vector` (the 0x000EBFD1 finding). Without them the same body at the same local count is 2251/6/26/8.
6. The tree view is held in a local `htree`, which is one more surviving local than WB's set.

## The surviving-local count

The 0x00561564/0x000EBFD1 lever applies here with full force. A chain of N pointer copies of `tree` gives byte-identical code whether it sits at the top of the function or just before the blend. In the intermediate shape (parenthesised blend member, unparenthesised TPA member) five different spellings of one more local (`htree` at two positions, a reference to the second transform, a chain of one, `htree` plus the shared `i`) compiled to identical bytes; in the final shape the reference to the second transform no longer equals `htree` (2237/0/55/1). The shared `i` is count-neutral. There is no period of 8 here: the scan to N=25 found the good counts only near N=1 (with parentheses) and N=9..10 (without).

WB's own local set (16 named locals) is N=0, which never did better than 2251 bytes and 7 regions in any shape. Retail therefore has more surviving symbols than the WB-faithful reconstruction, and they are probably not user locals: every named local in WB's debug frame has a counterpart here. The likeliest source is inline internals that the private views do not reproduce faithfully (the real `Matrix3D`, `Vector4`, `HTreeClass::Get_Transform`, `ShareBufferClass::Get_Array`).

The outer parentheses behave like a count of their own, per helper: over all 64 subsets of the six output rows the result depends only on how many blend rows and how many TPA rows carry parentheses, not on which ones, and all six (with `htree`) is the best subset (`rp111111`; the next is 4/49/5 with the blend rows only).

## Ruled out this run (do not repeat)

- Forced retail leaf order with nested parentheses in the old per-vertex blend: X row order right, every product pick flipped (2251/16/62/22).
- Parentheses in Get_Matrix3D (`(A*B)*2.0f`, `(float)(...)`, outer parentheses on the nine element expressions), `2.0f*A*B` (inert), outer parentheses on the TPA x, y, z lines, reading the quaternion through a `const Quaternion &` in Get_Matrix3D or the single path: all worse or inert on the new body.
- Empty inline constructors on the matrix (inert) or on the row type (much worse); separate `a`/`b` declarations and `/100.0f` weights (inert); `htree` declared before the guard (4/49/5).
- The old per-vertex helpers with WB's single-path expressions (`sq`, `sr`, `srp` in the generator) at counts 0 to 11: best 2251/6/53/8.
