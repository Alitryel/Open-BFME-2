## New target evidence: the WorldBuilder twin

`wb_show.py` has no pairing for this RVA, but the WorldBuilder body of this function is WB `0xA361E0` (436 bytes). It was found as the only unnamed WB function near the Grid twin (`0xA38240`) that calls `DXWrapper::Get_Transform` (WB `0x9C1560`) and switches on `this+0x0C`. It is ZH's `mapper.cpp` body verbatim:

- three arms (Axis 0, 1, default) each call the 16-float `Matrix4::Init` (WB `0xA35C50`, which is `Row[i].Set(...)` four times) with exactly ZH's values;
- `Matrix4 mat;` then `DXWrapper::Get_Transform(2, mat)`;
- `Matrix4 mat2(mat[0].X, mat[1].X, mat[2].X, 0, ...)` through the 16-float constructor (WB `0xA363A0`: vector constructor iterator, then `Init`);
- `tex_matrix = tex_matrix * mat2` through the cdecl friend `operator*` (WB `0xA36410`, the ROWCOL macro evaluated right to left, built through `Matrix4(Vector4 x4)` = WB `0x9AA2F0` -> `Init(Vector4 x4)`), then the user-written `Matrix4::operator=` (WB `0x9A5D10`, four `Vector4::operator=` calls).

BFME 2's `Get_Transform` (WB `0x9C1560`, `dxwrapper.h`) has the cases WORLD (bit 0x40000), VIEW (bit 0x80000), PROJECTION (transpose of a static matrix) and a default that prints "Reading back raw matrices from DirectX not allowed any more." and calls `Make_Identity`. Each non-identity case is `m = <matrix>.Transpose()` with the member `Transpose` (WB `0x9AA1B0`, four `Vector4` temporaries into `Matrix4(Vector4 x4)`). This is the shape `fxshadernamespacesas.cpp` already models for the matched out-of-line copy at `0x000768FE`. The bank's `bfmestages` shim instead carries ZH's version (WORLD, VIEW, and a D3D `GetTransform` fallback), which is not BFME 2's header.

Retail's stack slots confirm the layout: the four view scalars kept in memory and the two later spills sit at `esp+0x38+4*k`, which is the home of `mat` (0x40 bytes ending at the 0x78 frame top).

## The faithful model and what it shows

`envmapper-001854e0-20261020-w5-faithful-model.cpp.txt` (same directory) is a self-contained model of the WB-confirmed source: ZH body verbatim, BFME 1 `Vector4`/`Matrix4` plus ZH's 16-float constructor and `Init`, and BFME 2's `Get_Transform`, all `__forceinline` as `WWINLINE` is. It compiles to retail's switch block byte for byte and to retail's frame (0x78) and slot layout, but emits 1201 bytes (242 instructions). The divergence starts at +0xAF: the model keeps view element `view[1][0]` (`mat[0].Y`, product column 0, row 1) in memory from the start, where retail holds it in xmm4 and spills it at its first use (+0x140). The column-0 dot product is then reassociated differently.

## Ruled out, and what is left

The compiler revision, the SSE level, the optimisation level, the copy constructors and every header detail visible in WB are ruled out as the cause: none moves the model toward retail. The sink diagnostic shows the model's memory homing of `mat[0].Y` is not a small priority gap, since two extra straight-line reads do not give it a register. The dead `Get_Transform` cases do change the result (VIEW only, ZH fallback and BFME 2's four cases all compile differently), so the inline expansion of the unused cases feeds the allocator.

A non-empty release `DEBUG` macro in the default case is ruled out by target evidence: the matched out-of-line copy of BFME 2's `Get_Transform` (`0x000768FE`, `fxshadernamespacesas.cpp`) is byte-exact with a default case that only calls `Make_Identity`. Compiling an earlier Init16 user (ClassicEnvironmentMapper's body) into the same unit changes nothing either (`h9_tuctx.cpp`, 1201 B, 9/49/18).

What is left: the faithful model is the source shape the target evidence supports, while the bank is a farm permutation over ZH's D3D-fallback header. Retail behaves like the bank in one respect the model does not reproduce: `mat[0].Y` is register-allocated until its first use. No evidence points to a remaining header, flag or compiler difference that would explain this, so no further justified experiment was identified.

Raw evidence: every trial source, its disassembly (`*.cpp.dis`) and its align log (`*.cpp.align.log`) are in `build/w5env/` of the seat; `retail.dis` is retail's disassembly, `wb_helpers.log` and `wb_opmul.log` hold the WB helper bodies.
