## What the new bank is

It includes the real `vector3.h`, `vector4.h`, `matrix3d.h` and `quat.h` from the BFME 1 reference WWMath directory (same include set as `Rva000EBFD1UpdateVertexBuffer.cpp`) and drops `BfmeSkinRow`, `BfmeSkinMatrix`, `BfmeSkinTreeView` and the `htree` local. The matrices are `Matrix3D`, scaled with `Vector4::operator*=`. `HTreeClass` is a minimal declaration with BFME 2's compact pivot layout and a `Get_Transform(int)` returning the pivot's `BoneTransform`; the BFME 1 `htree.h` and `reference/shims/bfme2htree/htree.h` both declare Matrix3D pivots and cannot be used. The locals are WB 0xA0E990's sixteen (`streams`, `i`, `src[2]`, `runs`, `bonelinks`, `vi`, `remaining`, `cnt`, `bone0`, `bone1`, `w0`, `w1`, `tm0`, `tm1`, `j`, `tm`) under WB's types (`cnt` is signed: WB compares it with `jle`).

Two pieces of steering remain:

1. One extra surviving local. WB's set alone is 2251/7/66/18; every single extra local restores 0 regions, so retail has one more surviving symbol than WB's debug frame shows. The bank uses `unsigned short *run = runs;` for the run record. No local of that kind exists in WB, and the real headers did not supply the missing symbol.
2. `SkinMatrix3D`, a class derived from `Matrix3D` that carries the blend member (WB 0xA0ECA0 is a thiscall on `tm0` reading both matrices' rows directly, so BFME 2's `Matrix3D` has that member; the BFME 1 header does not). Plain `Matrix3D` locals give 2237/10/79/18 whether the blend is reached through a cast to the derived class (reading the second matrix through `operator[]`, or through `Row` under a diagnostic `#define protected public`) or is a free function reading `Row` under the same diagnostic define.

## What decides matrix a's Z picks

Retail matrix a (bone0) folds Z in `xz`, `zw` and `yz` (+0x171, +0x184, +0x210); matrix b loads it. Expressed as load preference, retail a is Y>X>W>Z, retail b and both of ours are Z>Y>X>W. `build/w2-16b680-r2/pick.py` prints the twelve product picks of an object.

Inert for these picks (all measured on the new shape): caller copy locals at the top or before the matrices (0 to 12), all 24 statement orders of the single-bone helper, swapping which bone builds which matrix (the first expansion keeps its ranks), `unsigned int` or swapped bone declarations, pivot layout displacements, a pivot reference or pointer arithmetic inside `Get_Transform`, extra symbols placed in the scale loop, the blend or the single-bone helper, `Rotation[2]` for Z, swapped operand spellings and `2.0f*` first.

What moves them is the symbol numbering inside the two `Get_Matrix3D` expansions:

- A forceinline helper with one local, called k times at the top of the function or directly before the first matrix (both positions give the same picks), cycles a's `xy`, `xz` and `xw` and b's `xy`, `xz`, `xw` picks with period 8 (k = 1, 7, 8, 9, 15 and 16 give the base picks). It never moves the Z picks.
- A `const Quaternion &` or a `const Vector3 &` to the translation declared inside the helper before the nine products changes the ranks; the same reference declared after the products does nothing.
- Whether the matrix argument needs a derived-to-base conversion (`SkinMatrix3D` against plain `Matrix3D`) changes the ranks of that expansion.
- With a translation reference declared first in matrix a's helper only, plus one inline symbol before it, all twelve picks equal retail's (`skin-0016b680-20261020-w2b-picks.cpp.txt`), but the blend then gains 5 structural regions (2237/5/48/3), and no caller local count from 0 to 11, with or without row parentheses, removes them. With the translation reference in both helpers, `tm1` as a plain `Matrix3D` and one inline symbol, all twelve picks match too, at 2235/14/62/21.

So retail's first expansion has a different internal symbol structure from its second, which a single shared helper written as in WB cannot produce. Likely candidates are a difference in how retail's `Matrix3D` blend member and its `Get_Matrix3D` argument are typed (the conversion effect), or one extra inline symbol ahead of the products in the first build. The numbering couples to the blend's picks, so the matrix picks and the blend have to be solved together.
