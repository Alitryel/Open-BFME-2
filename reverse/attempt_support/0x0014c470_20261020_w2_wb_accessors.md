## What closed the structural regions

All three changes follow the WorldBuilder debug twin (`python tools/wb_show.py 0x0014C470 --gd`, WB 0x009CC5B0, mesh.cpp lines 1517 to 1627) and keep the semantics of the previous bank.

1. `MeshClass::Peek_Model()` (WB 0x009B3020) as the argument of the holder factory 0x00136090. This put the model pointer in `eax` and the holder address in `ecx` at +0x69, as retail does, and swapped the two inlined holder-release tails (+0x54E and +0x8C7) into retail's order.
2. A reference local for the setup's parameter list, read through an inline getter (WB 0x009B35E0 returns `this+0xC`), in both the recolored loop and the FX lookup, with the copy for `UpdateParameterList` taken from that reference (WB copies from `local_ac`). This moved `mov ebp,[setup]; add ebp,0xC` ahead of the `AsciiString` temporary at +0x36F.
3. An explicit `return` at the end of the `recolored` branch, with the rest of the function no longer in an `else` (WB 0x009CC79F releases the holder and jumps to the epilogue). This fixed the setup reload order before the third effect handle call at +0x270.

## Remaining mismatch: stack-slot packing only

Frame offsets below are relative to the local area (esp+0x10 after the four register pushes).

| Variable | Retail | Ours |
| --- | --- | --- |
| model holder (RefCountPtr, unwind dtor 0x0007B724) | 0x08 | 0x0C |
| EH conditional-temporary flags, recolored loop texture, recolored single texture, FX record texture | 0x0C | 0x08 |
| `textureIndex` (n), `AsciiString(source.name)` temporary | 0x10 (with the second effect handle) | 0x08 (with the flags) |
| second effect handle, legacy texture | 0x10 | 0x1C |
| first effect handle, FX name string | 0x14 | 0x10 |
| setup spill | 0x18 | 0x14 |
| third effect handle | 0x1C | 0x1C |

The guard byte (0x03) and the condition bool (0x07) already agree. Retail's unwind map (FuncInfo 0x00D0AE5C, 17 states) confirms the holder at `ebp-0xEC` and the flags at `ebp-0xE8`; ours has them at `ebp-0xE8` and `ebp-0xEC`. All texture-like owners, including the three effect handles, unwind through `??1?$RefCountPtr@VTextureClass@@@@QAE@XZ` (0x0017098D); the guard through `??1BFMEDX8DeviceLock@@QAE@XZ` (0x00042F8C).

Diagnostic probe (scratch only, not semantic): removing both `textureIndex` and the `AsciiString(source.name)` temporary flips the holder and flags slots into retail's order; removing either one alone does not. So in our build those two join the flags' slot, and that slot then outranks the holder; in retail they share the second effect handle's slot instead. The next experiment should find a source shape that keeps them out of the flags' slot. Before the explicit-return change, removing the recolored loop texture also flipped the order; after it, that no longer does.

## Ruled out this round (each measured, none closer)

- Callee visibility (the fleet's `__declspec(noinline) inline` lever): visible bodies of 0x00136090 (with and without a visible 0x001007B0 setter), 0x0015148D, 0x00132A93 and 0x0007B9EE (with and without a visible 0x000424BB copy constructor) left the body byte-identical. Every local here has a destructor, so its address already escapes into the unwind funclets.
- Handle types: making the textures, effect handles and legacy handle one `RefCountPtr<TextureClass>` type, with or without a declared copy constructor, was byte-identical.
- More WorldBuilder accessors: `IsBound()` (WB 0x009A0990) at all six sites, a name-ID accessor (WB 0x009B49D0), `operator->` on the holder, MeshModelClass-level `Uses_FX` and `Peek_FX_Shader(0)`, the SAGE `RefCountPtr` with its `Create_Peek` friend: all byte-identical.
- Loop shape: WorldBuilder's `continue` form of the annotation loop was byte-identical; declaring `textureIndex` earlier in the loop body made it worse (4 regions, 61 memory, 60 register); hoisting `handles`, `count` and `description` above the `HouseColorEnable` test was worse (8 regions); widening the scope of the source description changed nothing.
- Effect fetch: declaring `effect` before the condition changed nothing; a named handle block for it emitted 2292 bytes.
- Lookup key and index: a named `AsciiString` key in its own block was byte-identical; declaring `textureIndex` before the annotation lookup was worse (2 regions, 53 memory, 48 register); reading the parameter list through the getter at each use instead of a reference local was worse (4 regions).
