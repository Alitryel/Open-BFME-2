## New discriminating findings

**First-count extraction changes exactly four later cash-computation instructions, and no loop instruction.** This is true independently in both contexts. Return-int and int-reference forms compile to the same body. Adding recount extraction is inert. See `base_first_ret_force.control-dis.diff` and `gh_first_ret_force.control-dis.diff`.

Before extraction, at base +234 or gh +239:

```asm
mov eax,[eax+88h]           ; warehouse boxes
mov ecx,[TheWritableGlobalData]
imul eax,[ecx+0A5Ch]
test eax,eax
```

After first-count extraction:

```asm
mov ecx,[TheWritableGlobalData]
mov ecx,[ecx+0A5Ch]
imul ecx,[eax+88h]
test ecx,ecx
```

The second sequence is retail's +23D..250 sequence. Byte lengths are unchanged, and the rest of each body is unchanged. Thus a genuine extraction/inlining boundary can survive into later operand scheduling **without altering the first scan, zero/vft allocation, query test, any stack home, or any loop**. It improves three aligned operand diagnostics but does not move GHZT. This independently separates cash-operand scheduling from the unresolved vft/zero/live-range knot. It does not establish why the compiler makes that choice, or that the original used a helper.

**Whole recount extraction canonicalizes away completely.** It does not change the purported local count/supplyCenter copy-propagation boundary after inlining in either context. This refutes recount extraction as the missing lever for the tested contexts.

**Loose-helper Boolean return does survive inlining and affects another scan's allocation**, but not in the desired way. In gh_loose_bool_force the recount changes from an ESI-held address `lea esi,[obj+258h]` to a saved address at `[ebp-20h]`, with ESI instead holding SupplyTruckAIInterface. Before aiDock it reloads the AI through that saved field address. It does **not** give retail's ESI=Object and repeated `[esi+258h]` loads. The loose reattachment count update becomes load/inc/store rather than retail's single memory inc. The body grows by seven bytes. The helper's true/false result adds no surviving helper call or explicit Boolean-return/test sequence; the differences occur in allocation and lowered memory operations.

The early ESI vft remains outside the repeating header in every gh force variant. At +EA it loads ESI; the outer latch jumps to **+EF**, skipping that load. A second materialization remains after construction restore: +5CB for first/count/recount variants, +5CE for loose/all. Retail instead has its single load at +F0, after repeating header +EC. All base force variants continue materializing the base vft locally into EAX at +1DB.

## Verdict and artifacts

The proposal's first assumption fails at the configured compiler's default inlining decision: ordinary inline helpers add calls absent from retail. Once force-inlined diagnostically, the stronger hope that useful extraction will repair the allocation knot is not supported by this finite family: recount erases entirely, first count changes cash operands only, and loose extraction changes allocation but worsens size/homes and still misses strict H. These results support keeping the semantic nested-loop guide and rejecting this family as a finishing source for now. They do not refute every possible future source-proven helper decomposition.
