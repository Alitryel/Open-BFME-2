Target facts (retail + WB twin build/wb/decomp/0xf9ce40.c lines 124-129): `dist = 0; range = getRange();
dist += range; pos.x = range*dir.x + pos.x; pos.y = range*dir.y + pos.y;` - range has no other use, so

Mechanism (toy build/bqt/s0.cpp reproduces our bytes exactly in a real-like loop; the dist variant
reproduces d1): MSVC 7.1 CSEs the x87->SSE transfer of the call result (`fst [ebp+X]; movss xmm0,[ebp+X]`)
and then multiplies from the register (`movaps xmm1,xmm0`). It does this however range is held:
static (z1), address-taken / passed to an opaque usef(&range) before, after or inside the loop (u1 u2 e2-e4),
returned (e1), array ref (z2), inline/forceinline ref or pointer helper (w1 w3), live later (x0 x1 y1 y2),
behind block boundaries (goto, do/while(0), if(list): b1-b3), `Real range = ...` init (c3), `dist = range`
(t6 c1), `dist += range` after the muls (c2), double-returning getRange (c4), declaration orders (s2 s3).
A multi-def SSE variable (dist, updated by addss in the loop) used as the scalar avoids the CSE and gives
the sequential schedule, but loads the scalar first (5 regions). Unknown-pointer stores plus &range (v2 v3)
also give sequential-but-range-first. Commutative operand order is canonicalized (source order inert).
Retail-pattern scan (build/bq/scan3.py: fst/fstp [ebp+X] then movss field + mulss [ebp+X] within 14 insns)
over matched rows finds the shape only in mixed x87/SSE matrix code (Rotate_Z, matrix scale) and one
3-component scaleInPlace (0x1F2819) - no plain call-result scalar case to copy.
