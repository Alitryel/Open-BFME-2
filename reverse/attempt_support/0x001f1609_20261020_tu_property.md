# 0x001F1609: the kept empty-destructor state is a property of one translation unit

Symbol `??1?$_Vector_base@PAVObject@@V?$allocator@PAVObject@@@_STL@@@_STL@@QAE@XZ`, retail RVA 0x001F1609, 43 bytes, RET0. Verdict of this pass: blocked; the existing bank `reverse/attempts/0x001f1609.cpp` is kept unchanged. Model: claude-opus-5-5. Toolchain: cl 13.10.3077 unless stated.

## Remaining mismatch

Retail keeps EH state 0 over `free(_M_start)` for the allocator proxy at this+8 (funclet 0x0076B1CA: `mov ecx,[ebp-10h]; add ecx,8; jmp 0x000B3FD0`, the shared empty `ret`), and has no normal-path call to that destructor. Every honest compile of the STLport 4.5.3 body (bfmealloc shim) gives the 14-byte frameless `mov eax,[ecx]; test; je; push eax; call free; pop ecx; ret`. `align_diff` on the bank: 14 B against 43 B, two structural insert regions (the `_EH_prolog` frame with the `[ebp-10h]` this-save and state store, and the `fs:[0]` restore with `leave`).

## New target facts

1. The shape is unique to the ObjectCreationList translation unit. A scan of every retail FuncInfo unwind action that reaches the empty return 0x000B3FD0 found 21. All matched ones except one either call 0x000B3FD0 explicitly on the normal path (an opaque empty destructor, as in `LivingWorldAI`, `saveGame`, `GameStateLoadGame`, `AptMpGameSetup` 0x004404AC) or protect a by-value argument (0x000CEF9F). The only states kept for an empty inline destructor with no normal-path call are 0x001F1609 state 0 (the proxy), 0x001F1634 states 3 and 7, and 0x001F21E8 state 0 (an allocator temporary at `[ebp-0Dh]`). All three bodies sit in the ObjectCreationList unit, and all three are banked or blocked on this same wall.
2. It is not a property of the `vector<Object*>` type. GameLogic's destructor (another unit, matched in `Code/GameEngine/Source/GameLogic/System/GameLogicDestructor.cpp`) frees its +0x164 member inline, although that member's unwind also uses the thunk 0x001F22A3, and the matched model of that member has no proxy state. Only ObjectCreationList code calls 0x001F1609 directly (0x001F16D8, 0x001F2055, 0x001F3105, the thunk 0x001F22A3 and the funclet 0x0076B19E). Other units reach the type only through 0x001F22A3 from their own funclets.
3. In retail, only two frameless 14-byte `free(start)` bodies exist, 0x0007FAB3 (the ICF fold of the POD vector destructors) and 0x00142D70 (basic_string). A frameless copy of this destructor would have folded into 0x0007FAB3.
4. Identity (a structural inference, not a new naming proof): 0x001F22A3 is a 5-byte `jmp 0x001F1609`. A controlled probe shows cl 7.1 emits exactly that thunk for a derived destructor whose base destructor it does not inline. `create` 0x001F14B6 destroys reallyCreate's by-value result through 0x001F22A3. This fits 0x001F22A3 as `~vector<Object*>` and 0x001F1609 as the out-of-line base destructor, so the pinned `_Vector_base` name stays. It does not support the bank's own lead that 0x001F1609 is `~vector`.

## Compiler mechanism, from controlled probes

- `/Od /Ob0`: the normal path calls `~_STLP_alloc_proxy` and the state is kept. `/Od /Ob1`: the call is inlined away and the state is kept, which is WorldBuilder's B09640 shape. `/O1 /Ob0`: the call is removed without inlining and the state is dropped. In every optimizing mode, cl drops both the call to an empty destructor and the unwind state that would call it. Retail kept the state but not the call. So in that unit the compiler inlined the proxy destructor on the normal path, but did not treat it as empty for the unwind map.
- The decision does not depend on whether the protected region can throw. With a C++-linkage, possibly throwing free inside `allocator<Object*>::deallocate` under /EHsc, the state is still dropped. What drops it is the empty unwind action.
- `#pragma optimize` cannot produce a mixed state. Implicit template instantiations take the pragma state at the end of the unit, and explicit instantiations take the state at their directive: whole groups compile unoptimized together. A scan of retail 0x1E8000 to 0x1F8000 found no unoptimized-style prologue.

## Ruled out in this pass (all give the 14-byte frameless body)

- /EHs, /EHsc, /GX, `/GX /EHa-`.
- Optimization settings: /Os alone, `/Os /Ob1 /Gy` without /Og, `/Og /Oy /Ob1 /Gy`, /Ox, `/O1 /Ob0`.
- Other switches: /Z7, /Zi, /Gm, /Gy-, /GR, /GF-, /Gd.
- Other compilers: 13.10.6030 (vc71-sp1) and 13.10.4035 (vc71-ddk-4035).
- A precompiled header (/Yc then /Yu).
- Unit content: a 4000-function unit (the probe placed before and after), a function with 40 or 300 EH states, `#pragma optimize` on/off pairs anywhere in the unit, and `extern template` or explicit instantiation of `allocator<Object*>` and `_STLP_alloc_proxy<Object**,Object*,allocator<Object*> >`.
- Destruction contexts: the destructor reached only as the base of `~vector`, only through a by-value temporary, only through a default-allocator local (which also loses the 0x001F21E8 allocator-temporary state), and only through the copy constructor's unwind.
- Link-time code generation: /GL with `link /LTCG /OPT:REF,ICF`, using the 13.10.3077 linker with msobj71 taken from vc71-sp1, an exported explicit instantiation in a DLL (n=1). This refutes the earlier explanation that the unit was built with /GL, at least for this standalone shape.

## What would move it

A source or compiler context in which cl 7.1 inlines `~_STLP_alloc_proxy`/`~allocator<Object*>` on the normal path but does not know it is empty when it builds the unwind map. Earlier passes reproduced the full 43-byte bodies and EH maps only with a dead `free` branch or dllimport-forceinline. Both were rejected for lack of provenance, and this pass found no legitimate construct that does the same. Because the three affected bodies share one unit, the next lead is the real ObjectCreationList unit context (its own headers, include order and the rest of its instantiations), compiled whole, not more single-body spellings. Reproduction probes and scripts: `build/w5_1f1609/` in the w5 seat (untracked).
