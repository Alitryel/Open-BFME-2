## Compiler facts (traced in c2 3077)
**Colouring order.** `colorElemental` (0x91426) visits elements by size ascending, then weight descending.
- It scans colours from the newest back to the oldest and joins the first compatible one.
- Compatible means: element size ≤ 2× the colour size, and no conflict in either direction.
- A colour grows when a larger element joins.

**Layout.** `StkColorCmp` (SP1 0x8E2D9) sorts colours by byte +0x18, then by weight×1000/size, highest first.
- Colours are laid out from ebp-0xC downward.
- An element sits at -(0xC + colour top + its own size).

**Weights.** `AddStackElement` (0x88642) adds 1 per IL reference.
- Address-taken locals at mode-1 or function scope get +2: two op-0x25f entities list every address-taken local in scope.
- Nested-block locals and mode-2 locals are not listed.

**Conflicts.** `ComputeLiveOnDef` (0x909B1, call sites 0x913b3 and 0x91db3) adds the live set at each reference.
- Every call "may use" the address-taken locals in scope. If one is not live-in to the block, it is treated as live through the whole block.
- Mode-1 calls also may-use every mode-2 local whose scope reaches the end of mode 2.
- Mode-2 calls never list mode-1 locals.

**Tracer bug fixed.** The earlier scratch tracer read conflict headers as first chunks, so every conflict set printed as empty. The "det2 has an EMPTY conflict set" note was an artifact of that.

## Target requirement
- det2 and wind1 must share one 8-byte colour with top -0xF4.
- That colour's total weight must be 3–5, to stay between view1 (703) and drift (328).
- det2 is coloured first, so it must create that colour. That means it must conflict with every earlier colour, including the mode-1-only det1, sx, sy and the mode-1 strings.
- wind1 must be nested (weight 3) and must not conflict with det2.

## Why it fails
Declaring det2 at mode-2 scope, or in a block reaching the end of mode 2, does give det2 a fresh colour (frame 0x634). But it also puts det2 in the getter call's block, so wind1 conflicts with det2 and the nested wind1 joins colour 10 instead.

## Resolution (second pass, 2026-10-20, about 70 minutes): exact
The previous pass named the unknown scope rule. This pass traced it with `build/agT/tools/blt.py`.

**Alias sets on calls.**
- Every call tuple carries a may-use list and a may-def list. Both contain the alias set of the address-taken locals in scope.
- A call to a C++ function that may throw (under /EHsc) also carries an extra may-use alias set:
  - inside a nested destructor EH state (an AsciiString temporary, a snapshot StringClass), it is that state's own set;
  - everywhere else, it is the last EH-state alias set created in the function. Here that is the scope at the final mode-2 RS(20,3) render-state name call.
- `extern "C"` D3DX calls carry no extra set.

**Why mode-1 calls "may use" late mode-2 locals.** That last set leaks the mode-2 scope locals into every throwing call in mode 1 and at function entry. `ComputeLiveOnDef` (call path 0x91891 / 0xa0bd7) adds every may-use member to the live set unconditionally.

**Fix: three source changes.**
1. Declare the getter `rva00094DD3` `throw()`. `__declspec(nothrow)` also matches. Its call then carries only its scope set. MSVC does not mangle exception specifications, so the getter's own unit still links.
2. Make mode-1 `wind` a tight block, at weight 3: `{ Rva00094DD3Val wind; getter(&wind); ...; }`.
3. Declare mode-2 `det` at mode-2 scope, so it stays in the last set.

**Result.**
- det conflicts with det1, sx, sy and the mode-1 strings, so it creates its own colour.
- wind1 does not conflict with det, so it joins that colour: {det w1, wind w3}, 8 bytes, weight 4, density 500. That sits between view1 (703) and drift (328), so the colour lands at -0xF4, as in retail.
- Relocations: all 68 symbols map to single retail addresses (`build/agT/tools/relcons.py`).
