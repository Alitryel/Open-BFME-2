# Debug realloc 6C4730: header reuse and intrinsic address ownership

Target `?rva006C4730@GeneralAllocatorDebug@@QAEPAXPAXIH@Z` is the complete
798-byte body at `0x006C4730..0x006C4A4E`, including RET12. The 785-byte
inventory prefix is truncated. The old bank's allocation, metadata, table and
cleanup logic was already correct; its 18 differing fixed byte positions were
confined to the backup-allocation footer. All prior RVA verdicts and linked
allocator handoffs were read before this attempt. Reconstruction took about
68 minutes, model=Codex-GPT-6; verification/publication are separate.

## Successful source shape

The stock MSVC 13.10.3077 compiler with `/O2 /MD` emits all 798 retail bytes
when the existing header variable becomes the capacity and a named pointer
is passed to the intrinsic `memset`:

```cpp
unsigned int h = ((unsigned int *)p)[-1];
if (!(h & 2)) {
    h &= 0x7FFFFFF8;
    h += 4;
} else
    h &= 0x7FFFFFF8;
char *t = (char *)p + h - 10;
memset(t, 0, 2);
```

Both parts matter. A separate integer capacity plus a direct word store folds
the LEA into the store (784 bytes). Per-arm named capacities, or the previously
tested separate capacity plus named-pointer `memset`, preserve the LEA but
spill the input pointer and change the loop allocation (814 bytes). Reusing
`h` with a direct word store still folds the address. The combined source above
keeps the native integer branches, join LEA, BX word store, 0x544 frame, input
in ESI and request-size LEA inside the retry loop. No added memory access,
dummy local, padding, branch, barrier, asm or compiler override is involved.

## Compiler observations and causal control

Read-only C2 traces of the bank, integer-capacity control and per-arm pointer
control reproduce their ordinary compiler output. In allocation round 2 the
bank's input-pointer candidate has cost 20, 11 references and priority 17;
the per-arm control has the same cost/references but priority 11. The backup
pointer has priority 16 in both. The original zero value also has cost 4 in
the bank versus 2 in the per-arm control. These are observed allocator fields,
not a claim that their formulas or every optimizer phase have been recovered.

An explicitly private diagnostic raised the input candidate's priority by six
in rounds 1/2 and increased nonnegative-cost fragments of the original zero
value by cost two/priority ten in rounds 1..3. That diagnostic reproduces the
whole retail body, isolating the two allocation decisions. It was never an
admission object or cache entry. The successful C++ above independently
reproduces the bytes using the unchanged compiler and normal verification.
Candidate indices are reused between rounds: identify fragments by their
origin symbol, not a fixed candidate number. Extending the zero intervention
past round 3 incorrectly changes later zero tests/stores.

The successful production source takes another route to those decisions:
round 2 records input priority 19 versus backup priority 16, and zero cost 2
with priority -40 (the per-arm control has zero priority -52). Thus the source
does not need to reproduce the diagnostic's exact cost numbers. It improves
the priorities while retaining the intrinsic's materialized address.

The useful lesson is to combine arithmetic-owner reuse with intrinsic address
materialization. Neither the earlier capacity-type/spelling family nor a
register-priority observation alone supplied the solution. Replay controls
and compact compiler evidence are in the companion directory.
