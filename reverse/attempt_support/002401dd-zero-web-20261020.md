## The exact remaining mismatch

1. **Zero constant.** Ours saves EDI at entry (before the `m_71` store) and executes `xor edi,edi` before the `ignoreCRCMismatches` byte compare. EDI then holds 0 through the `if (!m_1bc)` block and down to the stream null check (`cmp [ebp+8],edi`). Retail saves ESI and EDI together after the `m_1bc` compare (0x00240214) and creates the zero as ESI only after `closeWindows` (`xor esi,esi` at 0x0024023D). Retail's zero is live only inside the block, and the fetch temporary takes EDI there (ours: ESI).
2. **Stream register.** Retail loads the stream into ESI at the null check (`mov esi,[ebp+8]; test esi,esi`, 0x002402DD) and reads `m_04` through ESI twice. After that it is reloaded from `[ebp+8]` for `bfmeTakeEC`. Ours never gives the stream a register. Instead it opens a second zero web in ESI from the `frameName` constructor to `openFile` (`cmp eax,esi` for every `str()` null test, `mov [ebp-0x1c],esi`, `mov [ebp-0x14],esi`), and puts `""` into EDI from the `map` assignment on. Retail stores `map`'s `""` as an immediate and loads `""` into EDI only inside the `frameName` code (0x0024037D).

## What the diagnostics showed

Each diagnostic is a one-line change to the bank body, compiled once (n=1 each). None of them is landable, because each changes retail's bytes or adds dead code. Scratch sources, disassembly and align logs are in the seat's `build/w1_2401dd/`, one folder per trial.

- **The stream check is not the cause.** Removing the stream null check still leaves `xor edi,edi` at entry (trial d1).
- **The ignoreCRCMismatches byte compare joins the zero web.** With the flag compared against `true` (h1), the ESI and EDI saves move after the early exit, as in retail, and the `xor` moves down to just before the `m_1bc` compare. The `m_1bc` byte 0-compare joins the web the same way: with stream priority raised (k1), the `xor` still sits before it. Retail has neither compare in the web.
- **The dialog block's zero web is what costs the stream its register.** With the block compiled out of line (m1, m3), the stream takes EDI at the null check with no other change.
- **The stream's priority gap is two uses.** One extra straight-line use of `stream` (n1) gets it ESI only in the `frameName` segment. Two extra uses (n2) get it a register at the null check. In both cases the zero web still starts at entry.
- **A matched sibling behaves differently.** In `rva0023F8DA` (same unit, matched), the early-exit `m_6c` byte 0-compare does not join the zero web: its `xor esi,esi` follows the shrink-wrapped `push esi`. This still held with a second early-exit byte compare (probe p3) and with a guarded byte-compare block added (p5, p6). So whether a byte compare joins is not a fixed compiler rule. It depends on how the rest of the function's zero uses are allocated.
- **Inert, byte-identical to the bank or not closer:**
  - flag shape: a member instead of the global flag (h3), `char` views of both flags (e1), `m_1bc != true` alone (h2), moving `m_71 = true` (j1), the plain `if (ignoreCRCMismatches) return;` (j2);
  - control structure: the whole body nested under `!ignoreCRCMismatches || g_value12A6F38 == m_40` (i1), `if (stream) { ... }` (va), the WB order with an empty replay branch (vb);
  - declarations: `m_1b8` as a `GameWindow *` set to NULL (q1), a named zero local (z1), the dialog block as a `__forceinline` member (m2);
  - flags: `/G6`, `/Oy-`, `/Ob2`, `/Oa`, `/Ow`, `/O1` spelled out as its parts, and the `vc71-sp1` and `vc71-ddk-4035` compilers. `/O2` is far off (60 regions).
- **Ruled out by earlier verdicts and not repeated:** a local stream copy, a NULL compare, the map ternary, the `m_1b8` order, a size or buffer hoist, a `void *` buffer, a nested ignore check, `TheRecorder == NULL`, `m_1b8 = 0u`, `m_1bc == false`.
