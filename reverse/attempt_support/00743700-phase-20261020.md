## Phase effect (new finding)

Commutative add-chain order (len2/dot chains, XYZ vs ZYX) and scheduling in
this body depend on the function's total symbol count, not on where the symbols
are declared or what they are named.

- Dead `const float cN = 1.0f;` (or `const int`, `const double`) pads at any
  point shift the phase identically per symbol. `((void)0);`, `;`, `{}`, an
  uninitialised `float u;` and `if(0){}` do not shift it.
- Fitness over pad count k oscillates with period about 32. k=311 scores 0.91676,
  k=328 scores 0.91418, k=0 scores 0.90966.
- A probe of the segment loop alone (`loop.py` shape) with const pads reproduces
  retail's segment chain pattern (first chain ZYX, rest XZY) at k = 3..20,
  24..41, 66..73, 100..105 and 136..137.

Cross-check on the sibling SimpleStreakRendererClass::RenderStreak
0x00126433 (same phase effect, k=30 lever): symbols outside the function
(a preceding function's locals, file-scope globals) do not shift the phase,
the bank's named locals map one for one onto WB's `/Od` frame, and ternary
temps are inert. The missing count is not in the function's own locals; the
remaining suspects are named locals inside non-Vector3 inline helpers. See
`0x00126433_simplestreak_render.md`, "where the symbol count lives".

Consequence: judge a structural hypothesis by its best fitness over a pad scan
(for example k = 0..400 in steps of 1-4) and by per-region counts, never by a
single compile. Pads are a diagnostic, not a fix: once the structure is right
the real symbol count must land in phase by itself.

## Frame-order investigation (later sessions, 2026-10-20)

Best scratch score: the bank plus 8 dead `const float pzN = 1.0f;` before the
final `DX8Wrapper::Set_Transform(D3DTS_VIEW,view);` reaches 0.91134 (pro 32,
mv 73, tex 0, seg 63, isect 124, mid 171, tail 175). This is a phase pad, not
banked.

The largest shared delta is a permutation of six frame groups. Every other
slot is already at retail's offset.

| frame (shallow to deep) | groups |
|---|---|
| retail | top_normal 94-9c, bottom_normal b4-bc, **curr cc-d4, prev dc-e4, Z e8-f0, plT f4-fc, plB 100-108, view 10c-148**, offset 154-15c |
| ours | the same except **plT cc-d4, plB dc-e4, Z e8-f0, view f4-130, prev 134-13c, curr 140-148** |

Our order is a rotation of the source declaration order (view, prev, curr, plT,
plB, Z); retail's is curr, prev, Z, plT, plB, view.

The Length2 of prev and curr also differs:

- Retail reads X, Z, Y back from memory (5 refs per component).
- Ours reuses Z from the register and reads Y, then X (5/5/4). Dot follows the
  same pattern (retail X, Z, Y; ours Z, Y, X).
- This suggests retail's prev and curr pass through memory before Normalize
  (a copy or another producer); this is untested.

### Disproved (do not repeat)

- BFME2 Cross_Product or Normalize shapes differing from ZH: WB 0x71bce0 uses
  direct field stores and 0x71d310 inlines Length2 with Inv_Sqrt, both the
  same as ZH.
- Compiler-generated Vector3 copy ops: WB 0x71bb50 (59 calls, 25 B, int-mov

  trivial copies, so the copy op is user-declared, as in ZH vector3.h lines
  97 and 102. MSVC copies floats with integer movs anyway.
- WB 0x71f9e0 is unary minus via x87 `fchs` into the return slot (ZH shape).
- Variable names (hashing): every rename gave identical bytes.
- Symbol-id order via dead locals or pads: position is irrelevant, only the
  count changes the phase, and the six groups never move.
- Frame order by raw reference count: at -0x18/-0x1c retail places a 19-ref

- Frame order by loop-depth-weighted ref count: offset vs plT contradicts it.
- Already in history and re-confirmed: prev and curr at function scope, no

## Normalize x87 form per site (claude3, 2026-10-20)

Each Inv_Sqrt (call 0x4233a) Normalize ends in one of two forms. R retains
oolen (`fld [c]; fmul st(1); fstp [c]` x3, then `fstp st(0)`); C consumes it on
the last component (`fmul [c]; fstp [c]`). Sites are numbered in source order
(bank lines 1308..1587):

| site | line | object | retail | ours |
|---|---|---|---|---|
| 13 | 1426 | segdir | C | C |
| 15/17/18/20 | 1458/1478/1486/1506 | intersection Direction | C | C |
| 21 | 1510 | start_pl after Cross_Product(TOP dir, BOTTOM dir) | **R** | C |
| 22 | 1560 | new_direction after Cross_Product(prev, next EdgePlane) | **R** | C |
| 23 | 1578 | merge `pl` | C | C |
| 25 | 1587 | new_direction after Cross_Product(curr EdgePlane, pl) | C | C |
| all others | | | R | R |

Only sites 21 and 22 differ, and the difference does not depend on the phase:
it survives pad counts 0, 8, 311 and 328. Both sites normalize a stack Vector3
directly after a Cross_Product into it. Site 25 has the same shape and is C in
retail too, so the call shape alone does not decide the form. At site 21 the
fmul operand order of the cross product also differs:

- retail: `a.Y*b.Z, b.Y*a.Z / b.X*a.Z, b.Z*a.X / a.Y*b.X, a.X*b.Y`
- ours: `b.Z*a.Y, b.Y*a.Z / b.X*a.Z, a.X*b.Z / b.X*a.Y, b.Y*a.X`

Here a is the TOP Direction and b is the BOTTOM Direction, so the argument
order is retail's (ZH X = a.Y*b.Z - a.Z*b.Y). Untested: a cause in how
start_pl/new_direction are used afterwards (a Dot then a conditional copy or
negation), e.g. a separate named result vector, or `-start_pl` built through a
temporary.

## R8: the start `??_H` (2026-10-20)

Target fact (WB twin, `python3 tools/wb_show.py 0x743700`): the start of the
body is `DX8Wrapper::Set_Transform(D3DTS_VIEW, identity)` through the full
four-arm switch, as in the exact sibling `W3DAptRendererRva00111319.cpp`. The
WB-shaped start (scratch `vSV`, fit 0.85547 at /O2 base) differs from retail in
one place: ours calls the vector constructor iterator 0x00001423 for the
`Transpose` temp's `Vector4 Row[4]` at 0x74396F, and its frame is 0x14 larger.
Retail inlines that site and has `??_H` only at the tail `Set_Transform`.

The decision is a function-level c2 inline budget, and code after the site
counts:

- adding 120 or more volatile ops at the end of the body makes the start
  `??_H` appear in a variant that lacked it; 80 do not;
- removing code from the body (up to about 500 B, six probes) never removes
  the start `??_H`.

Refuted models: a fixed count of inlined `Transpose` calls (the exact
bfmeEnd982C inlines the 9th and calls `??_H` at the 11th), a `Vector4` count,
an `operator=` count, case-value order, and the device accessor spelling
(`D3DDevice->` member versus `_Get_D3D_Device8()`).

Flags on the WB start: `/Oy-` is the only setting that removes the start `??_H`
(fit 0.76462). `/Ob1` gives 0.86445 and keeps it.

The destination preamble (the `streakRender.cpp` link views, with `Transpose`
and the rows ctor `dllimport __forceinline`, plus the gsy `??_H` anchor) is
worse: fit 0.7786, with a third `??_H` at 0x743B65.

`permute.py` on the R7 bank: 207 trials, no gain.

`#pragma optimize("y", off)` before the R7 bank's body changes nothing (fit
0.91005, the same bytes).

Untried: weigh the volatile-op budget against named locals or temps rather than
bytes. The end-of-body probes suggest the measure is not plain code size.

## R10: the requirement is confirmed by compile (agAK, 2026-10-21)

The bank (`reverse/attempts/0x00743700.cpp`), compiled with "−2 fresh A"
emulated inside the running c2, comes out byte-exact: **14036 B, nd 0, 0
differing bytes** once the byte gate resolves the REL32s (47/47 calls; DIR32
masked).
- Emulation: during the compile, two unused D-pool numbers (X96/X97) are pushed
  onto the A free list (c2+0x1a79a0) at alloc event k. The next two A takes
  recycle them, and every later fresh A number drops by 2. The pool is never
  shrunk; shrinking it causes a C1001 ICE.
- It is exact at k = 2100, 3000, 3500, 4000 and 4400. The unpatched control
  gives 14049 B, nd 139.
- Tools: `build/agAK/symshift.py` and `batch.py` (untracked).

So apart from this one effect, the bank's source is complete and correct: in
retail, two A takes between Get_Transform's params and k≈4446 are recycled or
never needed. Any position in that window works.
