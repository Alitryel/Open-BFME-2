## Finding

Retail passes the reverse normal as a compiler temporary bound to prepare's reference parameter, not as a named local:

```cpp
node->second->source->respond(node->first->source->prepare(node->point, ContactVector(node->normal).negate()));
```

with a vector class that has a user-written copy constructor (WWMath `Vector3` style) and an in-place `negate()` that returns `*this`, and with both responses written as single expressions. Evidence: retail keeps `node->first` and `node->second` in EAX/EDX across the stores to the reverse vector, and so does this form, while every named-local form measured (the previous bank, `Vector3 r(n); r.X=-r.X ...`, `r = -n`, `r = -Vector3(n)`, `r(n); r = -r`) stays at 12 or more structural regions and 18 or more memory differences (324 to 368 bytes). The likely reason (an inference): for cl a named local whose address reached prepare in an earlier iteration may alias the node, a temporary does not. With the temporary, the single-expression responses also give `this` EBX, the normal pointer EDI and the first-response outer vtable EBP, as retail, with no extra uses. The bank's float-local spelling was only needed for the named local.

The negation shape depends on the vector class: the copy into the temporary and the in-place negation give retail's 12 x87 instructions (`fld x; mov r,[z]; fld y; mov [tz],r; fxch; fchs; fstp; fchs; fstp; fld tz; fchs; fstp`). Without the user-written copy constructor the body grows to 347 bytes. `-Vector3(n)` with WWMath's `operator-() const` gives the same 12 instructions in two temporaries (frame 0x18 instead of 0xC). WWMath's `Vector3(-X,-Y,-Z)` directly gives a plain load/negate/store per component, and `*= -1.0f` gives `fmul`.

## Remaining mismatch

Only local register choice and order in the three call sequences, all scratch registers:

- Test call (+0x94..+0xA7): retail pushes `&normal` through EDX and then loads the inner vtable into EDX; ours loads the inner vtable first and pushes `&normal` through EAX. After the inner call retail pushes the result and then reloads the receiver through EAX; ours reloads through ECX first.
- First response (+0xBE..+0xDD): retail loads `node->second` straight into ECX, loads the inner vtable into EAX after both pushes and reloads the outer receiver through ECX before pushing the result; ours goes through EDX, loads the inner vtable into EDX before the pushes and reloads through EAX after the push.
- Reverse response (+0x136..+0x13D): retail pushes the result before reloading the receiver through EAX; ours reloads through ECX first.

Read as register allocation: in the test retail gives `&normal` the same register as the inner vtable (EDX), so the vtable load cannot move above that push, and in the first response it gives the inner vtable the register of `&point` (EAX); ours gives them different registers and the load is scheduled first. The receiver reloads follow the same pattern (a reload through EAX must wait for the push of the result). Our compiler loads the inner vtable before the arguments in every form tried, including a standalone `g = b->prepare(p, n)` statement.

## Ruled out on top of the new bank (all measured)

- Flags: `/G5`, `/G6`, `/Ox`, `/Ob1`, `/Og`, `/Ow`, collisionmanager_impl.cpp's `/O2 /G6 /DNDEBUG /MD`, `// compiler: vc71-sp1` and `vc71-ddk-4035` are byte-identical; `/G7`, `/O1`, `/Ob0`, `/Oa` are worse.
- Signatures: prepare by pointer, by const or non-const reference; prepare returning `void *`, a class pointer, a reference or a const reference; `int` or `const` test; `bool` respond; const virtuals; virtuals split over a base and a derived class; all identical. A 4-byte info struct by value or by const reference is worse.
- Layout spellings: point/normal in a sub-struct, separate declarators, data pointers as an array or as reference members, `source` as a reference member, `(*p).f()`, a typedef cast on the receiver, the source class declared after the node: all identical.
- Inline accessors for point/normal, inline static pair helpers for the test and the first response: identical. Inline data wrappers for all three calls, or an inline `getSource()` on every receiver, only the inner ones or only the outer ones: worse (with `getSource()` everywhere the outer receiver is held across the inner call instead of reloaded).
- A non-virtual inline `prepare` over a virtual `doPrepare`, or a local for the inner receiver, at the test site only reproduces retail's test-call tail but caches `node->second->source` from the null test (330 B, 7/18/4); at the other two sites it is identical.
- Nested `if` blocks instead of `continue`, `if/else` for the state, the WorldBuilder twin's dead `checks`/`collisions` counters: identical; a `bool hit` local is worse.
