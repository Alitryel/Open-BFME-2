## Remaining mismatch

One block placement. Retail places the found arm's head (erase call, 0x10-byte allocation and record constructor call, retail +0xC7..+0x10F) directly after the not-found arm's head, and only the found arm's new-null and join blocks (+0x143..+0x154) sit after the inlined push node constructor. Our build places the whole found arm (head, null and join) after the push node constructor (ours +0xFA..+0x154). Inside that moved head the second-key copy for the constructor is also scheduled differently: ours loads `second` into edx before `push esi; push ecx`, retail pushes first and loads it into ecx. Everything else is byte-identical apart from relocations.

This is the same add-pair layout residue that blocks AptLinker::Load (0x006D1F80): both alloc/ctor heads first, then both new-null/join tails. Solve it once for both.

## Ruled out this run (all measured, sources and logs in build/w6d1d10/)

Inert (identical bytes to the new bank): loop spelled as the bank's while/break, as a for-return helper or as the WB begin/end iterator loop; `found` via `.node->entry` or `*find(first)`; user-written iterator copy constructor; erase helper visible as a noinline copy of the rowed 0x006D1C90 body or declared `throw()`; forceinline findByName, push_front or a const-key add helper; implicit `push_front(new X)` conversion; condition spelled `it == end()`, `end() == it`, `!(it != end())`, `it.node == 0`, `!it.node`; trailing return; an embedded list member object; a visible noinline record constructor; flags /G5, /G6, /Ox, /Ob1, /arch:SSE, /GF. Worse: push_front taking the Ref by value (482 B), erase taking the iterator by reference (`it` becomes memory resident, ebx zero register, 29 regions), comparison operator taking the iterator by value or a single-exit find (621 B, threading lost), early returns per arm (611 B, 660 B), /G7, /O1, /Os, /Oy-.

Diagnostics that explain the residue but are not landable: putting the erase in its own `if` before an `if/else` with identical push arms (t16), or writing the found arm first (t7), gives retail's head grouping (the hoisted form also gives retail's found-head key-copy order), but loses the cross-jumped push tail (661 B and 668 B): without the early merge the scheduler sinks the EH state store into the push sequence, so the two tails differ. Retail therefore has both the grouped heads and a tail merge made before scheduling. The found-first source also numbers the found arm's states 3/4 instead of retail's 5/6, which confirms that retail's source is not-found first, as WB shows. Making the two tails genuinely different (diagnostic e7) lays the arms out in plain source order, so the grouping does not come from the merge either.
