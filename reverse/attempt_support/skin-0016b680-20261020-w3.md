## New evidence

1. **The matrices are plain `Matrix3D` in BFME 2's source.** WB constructs `tm0` and `tm1` with 0x721BB0. WB holds 51 distinct `mov eax,ecx; ret` functions, so its link did not fold identical code, and 0x721BB0 is called by 30 debug functions that build `Matrix3D` locals (MeshClass::Cast_Ray, MeshClass::Intersect_AABox, HLodClass::Add_Lod_Model, HTreeClass::read_pivots and others). A derived class would have its own implicit constructor, compiled at /Od in meshgeometry.obj. `SkinMatrix3D` is therefore not the original type.
2. **The blend is a BFME 2-only `Matrix3D` member.** 0xA0ECA0 sits right after its first user in meshgeometry.obj, as an inline header function does (0xA0E850 `Vector3::Scale` follows `MeshGeometryClass::Scale` the same way). The vertex-and-normal overload (WB 0xA0F000) calls a second member of the same shape, 0xA0F390 (`ret 0x14`), and `BoneTransform::TransformNormalArray`. Neither member exists in the BFME 1 or Zero Hour WWMath `matrix3d.h`.
3. **The stand-in's effect equals a destructor.** Plain `Matrix3D` locals, a genuine `Blend` member declared in a copy of WWMath `matrix3d.h`, and one added line `WWINLINE ~Matrix3D(void) {}` compile byte-identically to the bank, also with both matrices declared at function scope. Without the destructor the same body is 2237/10/77/18. WB rules a destructor out as well: WB 0xA0E990 itself and MeshClass::Intersect_AABox (0x9CBA50), both of which build `Matrix3D` locals at /Od, call no destructor. So the steering is a property of BFME 2's `Matrix3D` type that gives its locals the treatment cl 7.1 applies to objects with a non-trivial destructor or a non-empty base class. Of the forms measured so far, only `Row` and `operator[]` in a non-empty base class of `Matrix3D` (seat w4, byte-identical to the bank) stay invisible in WorldBuilder. No target evidence shows such a base.

## Ruled out this run

Byte-identical to the bank: release-evaluated asserts at WB's three assert sites (`(void)(cnt<=vi)` after `runs+=2`, the pivot range in `Get_Transform`, the overlap test in `TransformPositionArray`); `__forceinline` on `Get_Transform`; two- and three-level derivation of the matrix type; the rotation as a `Vector3`-derived type plus `W`, or a `Vector4`-derived type; `Vector4` with `X`, `Y`, `Z` (or all four) in a base class, which is also inert on plain `Matrix3D` locals (2237/10/77/18), so the property sits on the matrix class itself; an earlier or later function in the unit that calls `Get_Matrix3D`, the blend, `TransformPositionArray` or `Matrix3D::operator[]` with `Vector4::operator*=`, so there is no first-expansion effect at unit level.

On plain `Matrix3D` locals with the genuine member (2237/10/77/18 unless noted): `tm1` passed by pointer to the blend; `Get_Matrix3D(Matrix3D *)` writing `(*m)[r][c]`; the same with `Matrix3D &m = *pm` (2235/9/54/11); class-level `operator new`/`operator delete`; no user copy constructor or assignment; matrices declared at function top, loop top or branch top (10/79/18) or in an inner block. On the bank, `Get_Matrix3D(Matrix3D *)` with `Matrix3D &m = *pm` gives 2237/10/76/18.
