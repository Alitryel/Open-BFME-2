## What closed the gap

Every earlier attempt sat in one of two register regimes, and neither is retail's. Retail keeps n in ESI, node in EDI, the iterator and then the y-midpoint in EBX, the object and then the x-midpoint in EBP, and the halved extent in its own parameter home.

1. The donor form (BFME 1 `Rva009441D0Recurse.cpp`: `extent /= 2` in place, repeated `ox + extent` sums, tail call for the last quadrant) is the right structure. With the old bank's goto-shaped pool code it gives n=ESI, node=EDI, iterator=EBX as retail, but the extent web wins EBP and the object is spilled. BFME 1's own retail at 0x009441D0 (in `lotrbfme.exe`) has exactly that allocation, so BFME 2 changed the push code, not the recursion.
2. A `half` local (the old bank's shape) gives half the top register (ESI) and the wrong roles everywhere.
3. The gap between the donor form and retail is one use. One diagnostic extra use of the object in the inner loop, or one fewer nested use of extent, flips the allocation to retail's exactly. Moving the node increment or the halving before the count test also flips it, but leaves a scheduling difference.
4. The natural lever is the pool pop as an inline helper with its size in a local (`int size = m_00 * 8 + 4;`) and the found path behind a forward `goto`. Written like the rowed 0x00141800 source without the size local, the helper keeps the donor's allocation and emits `push eax` for the known-zero arena. With the size local but the rowed `if (m_head == 0)` layout, the allocation flips to retail's but the found block stays inline (436 bytes, 2 regions). An `if/else` pop keeps the donor's allocation, and `while` or `for(;;)` pops emit 415 bytes. Only the `goto found` helper gives retail's allocation and also places the found block after the quadrant code. The old bank's goto code written directly in the loop body keeps the donor's allocation, so the helper's return value matters, not only its control flow.

## Ruled out in this run (all measured with align_diff, trial sources in the seat's `build/w5_142170/`)

- Callee visibility: a byte-faithful `__declspec(noinline) inline` copy of the pool grow (0x0006EFC8) in the unit changes nothing in either regime.
- STLport `slist::push_front` with a custom pool allocator (STLport 4.5.3 here needs user `__stl_alloc_rebind` overloads): `_M_create_node` stays out of line under the unit's flags, and `/Ob2` changes nothing. A force-inlined push helper taking the value by reference or by value compiles identically to the plain body.
- `/Ob2`, `// compiler: vc71-sp1` and `// compiler: vc71-ddk-4035`: no change.
- For the reload order: comparison operand order (worse), explicit `my`/per-branch `mx` locals, `n / 4`, `&node[k]`, `extent = extent / 2`, `++node` before the halving, `return` on the tail call, `const` on the rectangle parameters, the count test nested instead of an early return, `!node->count`, and a `while` drain loop. All keep the swapped reload order.
