## What changed and why

1. The single-target exit is `return;` inside the loop instead of `break;`. WorldBuilder 0x10A115B..0x10A1196 destroys the range result and the filter on that path and returns directly, separately from the normal loop exit at 0x10A117C. With `return` the front end emits two destructor calls of the result, which retail's tail merge folds into one; the extra reference raises the result handle's weight before stack layout. That alone moves the result handle to `ebp-0x1C`, radius to `ebp-0x20` and toObj to `ebp-0x2C..-0x24`, exactly retail's homes. Refuter (not observed): the frame homes staying at the bank's `-0x2C`/`-0x1C`/`-0x28` after the change.
2. Canonical headers: `PartitionRangeQueryCallView.h` (PartitionManager, BfmeWideResult with nothrow `next()`) and `Lib/Coord3D.h` replace the bank's private copies, which `tools/class_gate.py` refused. The coordinate set and subtract steps became two file-static inline helpers; the bytes are identical. The bank now passes the class gate.
3. WorldBuilder spellings that compile byte-identically were adopted: no `minRange` local (WB reads `m_134 * m_134` after the distance call), `Dot_Product(facing, dir)`, and `source->getTransformMatrix()->Get_X_Vector()` for the facing fallback.

## Remaining mismatch

Only the register assignment of two variables differs: retail puts `position` in EDI and the loop object in EBX, we do the opposite (and so schedule the `mov reg,[ebp+0xC]` load three instructions later around the iterate call). Everything else, including SSE roles, the x87 cone code and the EH states, matches.

The gap is tiny. A diagnostic `g_sink = (int)position;` placed three `if` levels deep inside the cone block (scratch only, not landable) flips the assignment to retail's and leaves only the sink store as a difference (register 0, 1 region). Removing one object use in the height block flips it too. So retail weighs `position` slightly above the loop object, by less than one deeply nested use.

## Ruled out on the improved body (all byte-identical to it unless noted)

- Loop forms: `for (obj = next(); obj; obj = next())`, `while (Object *obj = iter.next())`, `for (;;) { obj = next(); if (!obj) break; }`, and the object declared at function top, with or without `= 0`.
- WorldBuilder control shapes: the cone Boolean with `(!in && !m_13C) || (in && m_13C)`, inverted cone arms, positive `v1` nesting around the rest of the body, `Bool ok = v14(...)` with `radius <= G`, `&&` merges of the min-range and single-target tests, and the Mumakil Boolean with a named 10.0 constant.
- Callee visibility: `next()`, the range-query forwarder 0x00625610 and the distance leaf 0x002615E3 as visible `__declspec(noinline) inline` copies (all inert); the result destructor visible (worse, 6 regions); the height helper made invisible (inert); `throw()` on Cos, Inv_Sqrt, v1 and v14 (inert); virtual inline filter destructors (inert).
- Coordinate spellings: pointer-parameter set/sub (inert); copy-initialising toObj or delta from `*pointer` (much worse, 12 to 17 regions); an object-position pointer local (inert).
- Flags added to the bank's `/O1 /arch:SSE`: `/G7`, `/G7 /Ob2`, `/G7 /Oy-` (inert); `/G7 /Ot` (much worse, 51 regions).
