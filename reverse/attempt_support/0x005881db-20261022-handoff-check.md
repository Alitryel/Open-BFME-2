# updateMeleeAttack 0x005881DB (2199 B): handoff claim checked, 2026-10-22

A handoff (`Open_BFME_2_Recovery_Handoff_2026-10-22.md`) claimed a source-only
full 2,199-byte match via "a `volatile` list-node cursor paired with a separate
ordinary pointer holding the next node for the loop's comparison and
advancement". The claim is not in this repo: no ledger row exists for
`0x005881DB`, `HordeMeleeAmoeba.cpp` on master has no `updateMeleeAttack`
definition, and no fleet workspace holds a `volatile` variant of
`reverse/attempts/0x005881db.cpp`.

## What retail actually does at loop 1

    init   588232  mov ecx,[eax]      ; node = head->next
           588238  cmp ecx,eax        ; node != head  (register)
           58823A  mov [ebp+0x60],ecx ; spill node
    body   58824C  mov eax,[ebp+0x60]
           58824F  mov edi,[eax+8]    ; unit = node->object  (reload)
    latch  58835E  mov eax,[ebp+0x60]
           588361  mov eax,[eax]      ; node = node->next
           588366  cmp eax,[ecx]      ; compare the computed value (register)
           588368  mov [ebp+0x60],eax ; spill node
           58836B  jne 58824C

The comparison always uses the register and the store follows it. A `volatile`
pointer forces a reload *before* every comparison, which is the opposite order,
so the claimed transformation cannot produce this body.

## Conclusion

The bank remains the best body: 2196/2199 B, one structural region. The residue
is the c2 allocator colouring loop 1's node to EBX (and giving it slot 0x70)
where retail splits it per reference and keeps it in memory at 0x60. Mechanism,
proof of sufficiency and disproven source shapes are in
`reverse/attempt_support/0x005881db-c2trace-20261021/README.md`; this session
adds that the 2026-10-22 handoff's volatile claim is one of those disproven
shapes, and that the flag sweep is now done (no gain).
