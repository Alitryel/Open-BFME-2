## Result and important distinction

A semantics-preserving combination DOES achieve the build-list guard, an early ESI base-vft load, zero in ECX, and a direct `test eax,eax` for the partition query. This refutes the stronger claim that restoring on both exits necessarily prevents this allocation. It does NOT achieve retail's exact H discriminator: retail's vft relocation is +0xF1, in `mov esi,imm32` at +0xF0, reexecuted from the loop's +0xEC header. Our combination loads it before the repeating header, and emits another vft reload after a factory-success path. No tested variant has retail's single +0xF1 vft relocation.

The useful source combination is:

1. Change `if (supplyCenter) { body }` into `if (!supplyCenter) continue; { body }`.
2. Restore on exhausted template search in its condition: `while (tTemplate || (m_player->setCanBuildUnits(canBuildUnits), false))`.
3. On factory success, leave the string's scope with `goto factory_done`. Place the success restore at that label outside the template loop; the exhausted path jumps past it to `templates_done`.

No new flag, volatile access, asm, dummy use, equal-arm operation, or compiler setting was introduced. The baseline contains an inherited `_ReadWriteBarrier()` in the loose loop. Allocation comparisons initially retain it; explicitly named nobarrier/f_nobar/clean variants remove it. Only those versions can be considered free of that inherited lever. Unused original helper declarations remain unchanged.

## Path/semantics audit

- Empty template list: the short-circuit OR's RHS runs exactly once, restoring the saved canBuildUnits byte; loop never dereferences a null template; exhaustion jumps past the success restore.
- Exhaustion after unsuccessful templates: original template selection, findFactory calls, and next-template reads retain their order. The next header/condition sees null, restores once, and leaves. No per-iteration restores.
- Factory found: goto exits the success scope, so the AsciiString destructor runs before the factory_done restore. No next-template getter runs after success. The exhaustion RHS is not evaluated on this path. Exactly one restore.
- Cursor-null success forms: only the dead local cursor is assigned null; continue destroys the string, then next header/condition restores once. No template dereference follows the null assignment. These forms canonicalized to base.
- Scoped explicit-success-restore forms (`s_*`): an extra lexical scope encloses all factory-success operations so the string is destroyed before the explicit restore; the subsequent break skips the exhausted restore. No extra observable operation was added.
- Initial-empty guarded-do forms: initial null path restores before skipping the loop; nonnull path's exhaustion condition restores only on its final false evaluation; success restores after string scope then breaks.
- Build-list forms: getNext is read only after current body completes or an outer continue, just as in the original for increment. No speculative next pointer is cached across calls. Inner iterator continues retain their original loops. In w_* sources, only six classes of outer continues were changed to next_info gotos: non-supply, null source, null center where present, rebuild hole, empty/hostile warehouse, and sufficient total count. next_info still executes late getNext exactly once.
- Null center early continue skips only the former positive center scope; the end of that branch otherwise immediately reaches the build-list latch. It never enters the shortage/else branch.
- Positive query scopes skip precisely the same warehouse/recount work as the null-result continue. Query conditional/assignment forms end temporary filter lifetimes before entering either successor; an internal compare may move before the inlined vptr-reset stores, but there are no intervening externally visible calls or pointer mutations. They never bypass filter cleanup.
- Removed object-null tests are implied by DLINK_ITERATOR<Object>::done(): done() is m_cur==0, cur() is m_cur. There is no intervening call or mutation between the loop condition and cur(). No AI, center, warehouse, allocation or factory null check was removed.
- Exception behavior remains the original manual-restore behavior: a throwing call before normal exit does not gain a restore/RAII action.

Ten initial trials are DIAGNOSTIC ONLY: c01_exit_blocks, c02_exit_condition, c08_header_next_exit, c10_do_guard_exits, and b01/b02 crossed with c01/c02/c08. They execute success restore before the string destructor; this differs from retail and the base. Their .cpp/.diff are preserved only as clearly labeled counterexamples in all-results.csv/json. s_c01/s_c02/s_c08/s_c10 correct the ordering. None of the ten is offered as a candidate.

## Handoff
