## Hypothesis and outcome

Hypothesis: every earlier bank declared `rts::hash<NameKeyType>::operator()` without a body. The `_M_find` and `operator[]` instantiations the unit emits then hand `&key` to an opaque call, so cl treats `key` as address-exposed and gives it a slot for its whole scope. Retail's `_M_find` (0x002888D4) inlines the hash (`mov esi,[eax]` straight into the `div`), so retail's unit saw the body. With the body visible, every callee that receives `&key` is visible and does not leak it, `key` becomes unaliased, and its slot is packed by liveness. Since `key` is dead in the found branch, it then shares -0x10 with the found branch's AsciiString temporaries, which is retail's frame (key stored at +0x37 to [ebp-0x10], temps built at [ebp-0x10] at +0x79 and +0xC5, `&key` pushed again from [ebp-0x10] at +0x162). This is the same visibility lever that closed 0x00307EDC.

Refutation criterion, written before the first trial: with the hash body visible and the iterator padding removed, `key` keeps a slot distinct from the found-branch temporaries. Outcome: not refuted. The first trial (hash body only) removed the key and temp-slot differences; removing the iterator padding then removed the frame-size difference too.

## What else was established

- The volatile `getLoadType` getter is not needed: a plain in-class `int getLoadType() const { return m_loadType; }` gives the same bytes. Reading `ini->m_loadType` directly instead costs one structural region and makes the body 2 bytes shorter (395 B), consistent with the missing ECX load an earlier verdict described.
- push_back binds through the rowed `vector<const ModuleData *>::push_back` (0x004DFCB0) with its STLport body visible, as FXListStoreParse.cpp and ArmorStoreReload.cpp do. The unit's own copies of that push_back (49 B) and `_M_insert_overflow` (140 B, 0x002DFCF6) compile to retail's bytes with the bfmealloc flags. The real `vector<ArmorTemplate *>::push_back` gives the same parse bytes but would need a second fold pin.
- Binding operator[] through `ObjectLookupMap::findSlot` (0x0041F4E5) instead of a pin fails, whether findSlot is declared only or given as a visible `__declspec(noinline) inline` copy with its KeyToBucketMap::find declared only: both leave 16 memory and 6 register differences, because the nested find again receives `&key` opaquely. Making that whole chain visible would need private views down to `_M_find`, so it was not pursued.
- With the old bank's flags (no bfmealloc, `_STLP_USE_MALLOC`) the same fold proof fails at `_M_new_node` and `pin_problems` refuses the pin as a second identity at 0x0041F4E5. With the bfmealloc flags the operator[] chain bodies (63, 27, 73, 184 and 37 bytes) all equal retail's bytes with relocations masked.
