## What changed

The destroy loop has no for-increment; each arm of the type test advances the node itself (`n=n->next;` as the last statement of the particle arm, inside the handle's scope, and `else n=n->next;`). With that, the node is EDI, the nugget and then the hoisted particle ID are EBX, and the events-iterator reload `mov ebx,[ebp-0x1c]` sits before the jump into the shared `mov byte [ebp-4],1; call` list-destructor tail, all as retail.

## Why it works (diagnostic probes on the visible-erase bank)

The roles are decided by whether the node is referenced inside the particle arm, not by a weighted use count. Each probe was compiled and measured with `align_diff`; probe stores are scratch only.

- One `g_sink=(int)n;` store anywhere inside the particle arm flips the roles to retail's: after the nugget assignment (p07), inside `if(system)` (p09), and in the find loop's found path before `break` (p10). Each leaves only the probe store (1 memory line from the gate-filled load, 0 register).
- The same store at the loop-body top, before the type test, does not flip (p11: 3 regions, 9 memory, 1 register), although that block weighs more.
- Splitting the nugget's web from the type-test load also flips: a global store between the type test and `e=...` forces a second load of `[edi+8]` in the arm, and the node then takes EDI (p12). So the equivalent retail mechanism is either a node reference inside the arm at allocation time or a nugget web that starts inside the arm.
- Removing the nugget's use as the `findParticleSystemByID` argument flips the roles too, but the particle ID then goes to EDX instead of EBX (p01).

## Remaining mismatch

The particle arm's own advance is scheduled after the find loop and before the handle destructor's EH-state store (`mov edi,[edi]` ahead of `mov byte [ebp-4],4`), and that arm then jumps to the loop test instead of sharing retail's single `mov edi,[edi]` latch: +4 B (the moved load and a 2-byte `jmp`).

The WorldBuilder twin 0x945CC0 has a single for-increment (`L_94628e`, reached from both the type-test miss and the end of the arm), so this spelling is not the original source. It shows the mechanism; the original most likely referenced the node inside the arm in a way that cl later removes (WB reads `*it` again inside the arm for the nugget local `local_80`, which our cl merges with the type-test load before allocation).

## Ruled out in this run (each compiled and measured; identical to the visible-erase bank unless noted)

- Moving the arm's advance after the handle's scope (an inner block around the handle, or `if(type!=9){n=n->next;continue;}` with the advance after the block): cl merges the two identical trailing advances before allocation, and the old roles return. Respelling one advance (`reinterpret_cast`, `*(ListNode**)n`) does not prevent the merge. A `while` loop with the advance inside the handle's scope equals this bank.
- A `__forceinline` nugget helper returning the nugget or null: cl turns it into an `sbb` select and reshuffles the whole function (904 B, 3 regions, 26 memory, 14 register), although the node then takes EDI.
- `__forceinline` members for the whole stop body (nugget parameter, node parameter, type test inside) and an out-parameter helper assigning the nugget before or after the type test.
- The find loop as a `__forceinline` member taking the particle ID by const reference (drops retail's esp save at the erase call; worse).
- `while` and guarded do-while destroy loops, `register` on the node, the nugget declared at the loop top or before the loop (initialized or not), the node declared before the list, a base-to-derived `static_cast` nugget, integer and `short*` typed copies of the value.
- An explicit particle-ID local after the find-loop guard (`do`-while form: 2 register lines, worse; `for` form identical).
- `throw()` on `enable`, `destroy` and `Make001FCBD7`; a user-declared handle copy constructor; the TrackingPtr-style `if(!system)return Make001FCBD7();` operator->; `continue` instead of `else if` for the destroy branch; plain `inline` erase (cl still calls it out of line).
