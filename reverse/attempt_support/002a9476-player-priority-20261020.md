## What the candidate fixes compared with the bank

- No equal-arm ternary. The loop is the WorldBuilder form (`for (it = begin(), end = end(); it != end; ++it)` with `break`), and cl rotates it exactly like retail.
- The hash key is stored once. The bank's `(const unsigned &)key` cast created a temporary copy (a C-style cast to a const reference of another type is a static_cast that binds a temporary), which cost the extra frame slot.
- The collector map key is an rvalue from an inline `getPlayerIndex()` accessor, as retail's `mov eax,[ebx+0x54]; mov [ebp-0x10],eax` requires. A named `int` local or `(int)lvalue` does not produce that temporary in cl 7.1 (`(int)*(int*)p` still passes the member's address).
- With `getSide()` as an inline accessor and the dozer test written as `find(key) != end()` on a real `hash_map` view, every address-taken local and temporary shares retail's single `[ebp-0x10]` slot.

## The remaining mismatch, measured

Retail colours `it`=ESI, `this`=EDI, `player`=EBX, keeps `end` and `ai` in memory (`ai` in the dead `player` home `[ebp+8]`), and has no `&teams914` temporary. The candidate colours `it`=ESI, `this`=EDI, `&teams914` (begin load plus push_back receiver)=EBX, spills `player` for the loop and new-team region and gives it ESI only after the push_back join.

Gap probes (scratch only, never for landing), each a single `g_sink=(int)player;`. Items marked "candidate" were measured on the candidate; the others on an earlier form of it with a named map-key local, which differs only in stack-slot sharing and allocates the same way:

- In the loop body (candidate): retail allocation and every other byte equal (the third table row).
- In the found branch, or inside an `if` nested in the new-team block: the same retail allocation.
- Inside two nested `if`s, in the found branch or after the push_back (candidate): no change.
- At the top of the function, or straight-line at the end: overshoots, `player` takes EDI and `this` EBX.
- Inside an `if` arm in the army/dozer part: no change.
- Weakening `&teams914` instead, by putting push_back under a condition (candidate): the temporary disappears, but `end` then takes EBX and the loop de-rotates, so `player` also loses to `end`.

So the retail source gives `player` slightly more weight in the region before the push_back join than this body does: about one register-requiring use inside a single conditional or the loop body, more than a doubly nested use and less than a straight-line one. Every retail instruction in that region is already accounted for, so the missing weight has to come from source that leaves no instruction behind, or from a variable structure this run did not find. The bank's ternary reached the same allocation only through a de-rotated loop.

## Ruled out in this run (all compile to the same 332-byte allocation unless noted)

- Loop spellings: `end` declared before the loop, begin/end declared together outside the `for`, end-first declaration order, `while`, `continue` form, typedef iterator plus const_iterator end, `ai` declared after the iterators, function-scope `team`.
- Uncached `it != teams914.end()` (reloads end every iteration), search loop followed by `if (it != end)` (extra compare).
- Vector reached through a const reference or a pointer local: `player` wins EBX but the vector address replaces `this` in EDI (319 bytes, 15 regions).
- Element as a by-value local (removes retail's `[esi]` reloads) or as a const reference local (no change).
- Real `hash_map` find/end iterators, getSide twice instead of a reference local, `NameKeyType` key with reinterpret casts.
- Same-TU visibility of the ally check 0x004E94CA, a decl-only push_back specialization (335 bytes, still the temporary), an inline join helper (not inlined at `/O1`; `__forceinline` diagnostic gives 324 bytes, 18 regions), the `vc71-sp1` and `vc71-ddk-4035` compiler profiles, and `/arch:SSE` against none.
