## What moved

Reading the two vertex buffers through an inline `Get_Array()` accessor, as WorldBuilder does (`sub_9ddcc0`), instead of the member directly. It changes nothing in the code shape; it moves the blend's Y-row leaf order from a11, b11, b12, b10, a12, a10 to a11, b11, a10, b12, b10, a12 (retail a11, b11, b12, a10, b10, a12), which removes two register differences. The same accessor on the run and bone-link buffers is byte-identical to the old bank.

Adopted because they compile byte-identically to that body and follow WorldBuilder: the combined `runs==0||bones==0||tree==0` guard, `Get_Vertex_Count()`, an HTree `Get_Transform(int)` accessor, `Get_Matrix3D` as a member of the pivot transform, and the blend sum written in the order of WorldBuilder's helper (`a[r][0]*v.X + ... + a[r][3] + b[r][0]*w.X + ... + b[r][3]`).

## Remaining mismatch

- Matrix a (memory only): retail folds Z in `xz`, `zw` and `yz` (+0x171, +0x184, +0x210); we load it. Matrix b matches.
- Blend leaf order (memory and register): X row ours a02, a01, b01, b02, b00, a00 against retail a00, a01, b00, b01, b02, a02; Y row one swap (a10 and b12); Z row one swap (a20 and b22).

The load-first ranks of the quaternion components per matrix behave like arbitrary permutations that move with unrelated edits (retail b ZYXW, retail a YXWZ, ours a ZYXW, other trials ZYWX, WZYX, ZXYW), so they follow numbering over the whole function rather than the helper's spelling.
